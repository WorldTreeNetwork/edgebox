# Interface direction

**Intent.** A household member opening a local utility wants to find an action
quickly; an operator wants a quiet, trustworthy health overview. It should feel
like a well-kept field notebook, not a monitoring dashboard.

**Domain.** A shared tool shelf, labeled drawers, an index card, a household
noticeboard, a service-light, and a handwritten maintenance log.

**Color world.** Eggshell paper, graphite ink, moss leaf, clay warning marker,
rain-dark slate, and a brass focus ring. The component tokens use those names
so the UI does not become a generic gray dashboard.

**Signature.** Each capability is an _action card_: the verb phrase leads, the
provider sits below as supporting evidence, and an honest state chip closes the
card. This lets people act without first recognizing a product brand.

**Rejecting.** Metric-card dashboards → an action index; icon-only mobile
navigation → labeled controls; a green/red dot → a text-bearing status chip.

**Hierarchy.** Page title/search is the focal element; action labels use the
strongest weight, provider and timestamps are secondary, diagnostic detail is
tertiary. A compact 4px rhythm keeps controls practical while section breaks
remain generous.

**Depth.** Quiet paper surfaces use a fine warm border and almost no shadow.
Inputs are slightly inset. This makes controls legible without turning every
section into a card.

**Identity and settings.** Account and login components make the next action
explicit rather than imply an authenticated state. Passkey controls use native
dialogs for rename/removal, retain invalid input, and state the final-passkey
recovery boundary in ordinary language. Preferred apps show whether a choice is
saved, catalog-defaulted, or failed to reset without claiming resolver logic.
