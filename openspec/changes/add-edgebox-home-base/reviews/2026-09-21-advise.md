## Findings to reconcile

1. **Reset has two incompatible outcomes.** ADR 1, steps 2–3, and the deterministic
   preference requirement say that removing a preference falls through to the
   curated default, then the sole eligible provider, then the chooser. J08 says
   that no curated default means “choose next time,” which contradicts the
   sole-provider case. Reconcile J08 with the ordered resolver, or explicitly
   amend the resolver and delta if a separate reset behavior is intended. Pin
   reset stories/server cases for an eligible default, no default plus one
   eligible provider, several providers, and zero providers. An unavailable
   resolved default must retain ADR 1's explicit recovery behavior.

2. **Two advertised interactions lack an executable handoff.** The IA gives Home
   a direct search and gives application details “provider/default controls,”
   but J01–J18 do not define either action. Home search needs a destination,
   search scope, query preservation, and a story/test mapping. Application-detail
   preference controls need a capability-selection rule for apps supplying
   several capabilities, guest behavior, and a story/test mapping. A smaller
   valid resolution is to make those controls ordinary links into the existing
   capability flow and explicitly document that behavior. Do not leave the
   interface-kit and directory workers to invent different interactions.

These are bounded contract amendments, not a request to add product features.

## Architecture assessment

The central design answers the concerns from my independent pass. Categories,
capabilities, applications, endpoints, and observations have separate meanings.
Stable associations and session-derived preference ownership are appropriate for
the existing SQLite runtime. Migration-based seeding preserves user data and
does not turn a dated host observation into permanent success. Keeping the
starter table until separately justified avoids an unrelated destructive change.

Visibility is enforced before DTO construction, with an explicit, default-empty
operator allowlist. Approved links grant no application SSO, document access, or
container authority. Health checks have a bounded, fixed-endpoint threat model;
authentication responses and setup readiness are correctly distinguished from
reachability. The identity handoff explicitly addresses the current password
entry points, generic OAuth mismatch, account-linking proof, secure WebAuthn
context, credential ownership, recent authentication, and recovery.

The strongest tradeoff is curated inventory over discovery: it adds a deliberate
maintenance step but keeps a small Pi deployment understandable and avoids
giving the product Docker or filesystem authority. The future storage boundary
is appropriately deferred. No TLS/infrastructure changes are smuggled into
passkey delivery, and no live external service is required for ordinary CI.

Storybook-first development, headless interaction primitives, shared styling,
and reuse in app routes are explicit. The inventory otherwise covers meaningful
success, empty, pending, cancellation, error, authorization, and recovery states.
Four integrated journeys plus focused server/component tests are proportionate.
