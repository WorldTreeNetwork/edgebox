## Amendments verified

1. **Reset now has one contract.** ADR 1, the IA, J08, and the reset scenario
   all remove only the member's override and rerun the ordinary resolver:
   eligible curated default, otherwise sole eligible provider, otherwise
   chooser or no-provider state. Reachability does not redefine eligibility:
   an unavailable resolved default keeps explicit recovery and never silently
   selects another app. Failed reset preserves the preference. J08 names all
   five result stories plus failure, assigns the reset/resolution and ownership
   tests to catalog, and assigns reset feedback verification to directory.
   The former “choose next time” contradiction is absent from the current
   contract; it remains only in the historical review.

2. **Home search is executable as specified.** ADR 1, IA, J19, and the proposed
   search scenario agree on a labeled GET form from `/` to `/capabilities`,
   trimmed `q`, an unfiltered destination for blank input, capability-card
   results, and preserved query navigation. Matching covers capability text
   and associated visible application text; hidden associations cannot produce
   matches. J19 supplies ready/entered/blank stories and reuses the existing
   no-results story. Interface kit owns input/Enter/destination verification,
   catalog owns search and visibility tests, and directory's existing discovery
   journey owns the integrated URL/reload check. No extra search surface or
   E2E suite is introduced.

3. **Application details have an unambiguous handoff.** ADR 1, IA, J20, and the
   corresponding scenario specify an ordinary, individually labeled link for
   each visible capability from `/applications/[application]` to
   `/capabilities/[capability]`. Single, multiple, zero, and guest states have
   named stories. Links do not preselect the originating app or write a
   preference. Guests follow the same links and meet the existing sign-in
   requirement only when saving. Interface kit supplies the variants; directory
   verifies hrefs and absence of mutation controls; existing chooser/server
   tests retain authorization and write ownership.

## Scope and remaining implementation boundaries

The amendments reconcile advertised behavior within the existing scope. They
do not introduce new runtime dependencies, migrations, identity flows, service
administration, storage access, tracking, or extra integrated journeys. Server
visibility, approved launch endpoints, session-derived ownership, bounded
health observations, and the separate identity/security review remain intact.
Storybook-first development, shared styling, and accessible primitives remain
required. Living specifications still describe delivered behavior; accepting
this architecture does not claim that the proposed application exists.

Descendants must still finalize shared DTO ownership before parallel writes,
pin health limits during preparation, and verify the installed identity APIs.
Those are explicit existing handoffs, not unresolved findings in this amendment.
